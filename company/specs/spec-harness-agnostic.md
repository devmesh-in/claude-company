# SPEC: harness-agnostic company

_Type: feature. Author: CEO (sole developer, owner-directed). Date: 2026-08-23._
_Status: SPEC-READY. Tracking: #133 (this), #134 (cost ledger removal)._

## Part 1 - Product requirements

### Problem

The harness is welded to Claude Code. Enforcement is wired through
`.claude/settings.json` hook bindings, roles live in `.claude/agents/`, and the
installer assumes exactly one harness exists. Running the company on any other
agent CLI means hand-porting the whole surface.

That has already been attempted once. A DevMesh fork built a 569-line opencode
shim (`DevMesh/.opencode/plugins/company-harness.ts`, preserved unmerged on
`task/opencode-shim`). It was audited SHIP-WITH-FIXES with eight findings, none
fixed, and it drifted out of agreement with this repo's hook set - it lists a
`guard_invariants.py` that does not exist here and documents modes that were cut
by PR #126. Its most serious defect was not in the audit: it returned early for
every subagent session, disabling the entire guard chain in exactly the
delegated lanes where all code gets written.

The cost is not just opencode. Every future harness repeats the port, and each
port is an opportunity to ship silent non-enforcement.

### Goal and success metrics

The company runs on Claude Code and opencode, from one install, with the same
enforcement guarantees. Binary success criteria:

1. Claude Code behavior is bit-for-bit unchanged by this work.
2. A guard that blocks on Claude Code blocks on opencode, in main and
   delegated sessions alike.
3. Adding a third harness requires one renderer module and one adapter, with no
   change to the guards, the skills, or the roles.

### Users and personas

- **Owner / operator:** picks harnesses at install time, runs the company.
- **Contributor to this repo:** must have both CLIs installed to run the ladder.
- **Neither persona writes harness-specific role or skill files by hand.**

### User stories and acceptance criteria

US-HA-1: As an operator, I can install the company into a project and choose
which harnesses to wire.
  - AC: `install` presents the harness choice; selecting only Claude Code
    produces an install byte-identical to today's.

US-HA-2: As an operator on opencode, the guards enforce against me the same way
they do on Claude Code.
  - AC: a frozen-surface edit, a slop violation, and a secret in a staged
    commit each block on opencode, including from inside a subagent.

US-HA-3: As a contributor, I learn from a red gate - not from a user - when an
opencode release breaks our integration.
  - AC: the harness suite runs the real `opencode` binary and fails when a
    generated agent, command, or the plugin stops registering.

### Functional requirements

**Generation**

- FR-HA-01: `.claude/` is the sole source of truth and is never regenerated by
  this feature. No generator writes into it.
- FR-HA-02: `.opencode/agent/<role>.md` is generated from
  `.claude/agents/<role>.md` by frontmatter rewrite, body byte-identical.
- FR-HA-03: `.opencode/command/<name>.md` is generated per
  `.claude/skills/<name>/SKILL.md`, giving each skill a slash affordance. The
  command body directs the agent to load the skill; it does not duplicate it.
- FR-HA-04: the adapter's guard chains are derived from the hook bindings in
  `.claude/settings.json`, not hand-maintained. `EXPECTED_WIRING` in
  `guard_models.py` remains the single wiring assertion, unchanged.
- FR-HA-05: generated output is committed, and a gate regenerates into a temp
  tree and fails on any difference.

**Adapter**

- FR-HA-06: the adapter is dependency-free ESM JavaScript. No TypeScript, no
  build step, no `node_modules` in the payload.
- FR-HA-07: the adapter runs the unmodified `.claude/hooks/*.py` guards over the
  same stdin payload shape Claude Code sends.
- FR-HA-08: guards run in every session, subagent sessions included. Verified
  2026-08-23: `tool.execute.before` fires for a delegated `bash` call with
  `parentID` set to the parent session.
- FR-HA-09: a guard exiting 2 blocks the tool call and surfaces its stderr.
- FR-HA-10: a guard that cannot be spawned is a BLOCK, not an allow. The
  DevMesh shim resolved `code: 0` on spawn error, reading a missing `python3`
  as permission.
- FR-HA-11: tools are classified explicitly. Known write tools run their chain,
  known read-only tools pass, and an unclassified tool BLOCKS with a message
  naming it. Fail closed on an unknown surface. A fourth class exists for
  write-capable tools the guards CANNOT judge because the tool's arguments
  carry no file path or content (`apply_patch`, any `mcp__*` tool): those are
  refused with a message naming the reason, rather than routed to a chain that
  would inspect an empty string and pass.
- FR-HA-12: the payload `cwd` is the plugin's `worktree`, not a hardcoded root.
  REVISED 2026-08-23 after audit - the original wording overstated this.
  `worktree` is fixed at plugin load and no per-call cwd exists, so every
  payload in a session carries the same `cwd`; what makes the guards correct is
  that they resolve the acting tree from the FILE PATH, not from cwd. The real
  consequence is that `in_worktree_or_out_of_tree(cwd, root)` never fires under
  the adapter, so guard_provenance's worktree exemptions do not apply and
  opencode work is held to the stricter main-checkout rule. A deliberate
  tightening, recorded as such rather than claimed as parity.
- FR-HA-13: injected context is scoped per session. A single plugin-global
  buffer cross-injects state digests between concurrent sessions.
- FR-HA-14: the deny list from `settings.json permissions.deny` is enforced by
  the adapter, in all sessions, for reads as well as writes. opencode has no
  path-pattern permission syntax.
- FR-HA-15: opencode roles pin no model; the adapter blocks any per-role model
  override. Owner decision 2026-08-23: inherit the session model for now.

**Install**

- FR-HA-16: `.claude/` installs regardless of harness selection - the guards
  live there and the adapter shells out to them.
- FR-HA-17: harness selection appears in `install` and `update`, enumerated
  from the renderer registry rather than hardcoded, with detection
  pre-selecting. Flag form `--harness=claude,opencode`.
- FR-HA-18: when a project has an `AGENTS.md`, opencode ignores `CLAUDE.md`
  entirely. The installer detects this and offers to write an `AGENTS.md` that
  includes `CLAUDE.md`, rather than installing inert canon.

**Verification**

- FR-HA-19: a harness suite runs the real `opencode` binary
  (`debug config`, `agent list`, `debug skill`) and asserts every generated
  agent, every generated command, and the plugin itself registered. No skip
  path: a missing binary is a failure.
- FR-HA-20: a golden payload corpus asserts the adapter emits the same guard
  stdin payloads Claude Code does, for each wired event and tool.

### Business rules and validations

- BR-HA-01: no generated file is ever hand-edited. The drift gate is the
  enforcement.
- BR-HA-02: the adapter never reimplements a guard. If a rule needs to change,
  it changes in the Python.
- BR-HA-03: an enforcement decision must not depend on which harness is
  running. A harness may differ in mechanism, never in verdict.

### Scope

**In:** the renderer, the opencode adapter, generated `.opencode/`, harness
selection in install and update, the harness suite, docs.

**Out:**
- Cost tracking of any kind (removed outright under #134, landed first).
- Porting per-role model tiering to opencode (inherit for now).
- Any third harness.
- Any change to guard logic, skills, or role bodies.

### UX notes

Harness selection is a checkbox list in the install TUI, pre-checked by
detection. An opencode-only install produces no `settings.json` but still lays
down `.claude/hooks/` and `.claude/skills/`, which is unusual enough to warrant
one line of explanation in the installer output.

## Part 2 - Build readiness

- **Owned directories:** `lib/`, `.opencode/`, `tests/harness/`, plus targeted
  edits to `install.sh`, `update.sh`, `lib/install-tui.js`, `package.json`,
  `docs/`.
- **Invariants in play:** hooks stay Python 3.8 stdlib and fail open on internal
  error; `no_slop` applies to all writing; accepted ADRs are immutable; the
  tracked `company/gates.config` keeps its placeholder gates.
- **Frozen surfaces touched:** none by this feature. #134 supersedes
  `CR-2-freeze-gate-run-artifacts.md` for the two cost run-artifact entries.
- **Data model impact:** none.
- **Contracts impact:** the guard stdin payload gains a second producer. Shape
  is unchanged; FR-HA-20 pins it with a corpus.
- **Open questions and chosen fallbacks:**
  - OQ-HA-01: does opencode enumerate its tool list headlessly? `debug v2`
    does not. FALLBACK: ship a `known-tools.json` snapshot, assert the adapter
    classifies every entry, and refresh it on version bumps. Tag
    `// OQ-HA-01 assumption`.
  - OQ-HA-02: should an opencode-only install still write `.claude/skills/`,
    which opencode reads natively, or a copy under `.opencode/skill/`?
    FALLBACK: `.claude/skills/` only - `.claude/` is installed regardless, so a
    second copy would register the same skills twice.
  - OQ-HA-03 REVISED 2026-08-23 after audit: the question named a tool that
    does not exist. opencode registers `apply_patch`, whose only argument is
    `patchText` - no file path, no content. The original fallback (classify as
    a write tool, run the Edit chain) would have handed guard_frozen and
    no_slop an empty path and an empty string: they inspect nothing and pass,
    which is a bypass dressed as enforcement. DECIDED: refuse it with a message
    naming the reason. Two tests asserted on the nonexistent `patch` and passed
    forever, which is the lesson - a test over a subject that does not exist
    cannot fail.
- **Verification plan:** FR-HA-01 and 05 by the drift gate; 02, 03, 04 by
  renderer unit tests plus FR-HA-19 registration assertions; 06 by absence of a
  build step and a dependency check; 07 through 15 by adapter unit tests over
  the golden corpus plus targeted live checks against the real binary; 16
  through 18 by `tests/install` and `test_tui`; 19 and 20 are themselves the
  verification.
